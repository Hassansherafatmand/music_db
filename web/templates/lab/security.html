Why the attacks fail

Five ways the website protects the database and the listeners.

SQL injection

2

The sort menu is a fixed list

A parameter can't be a column name, so ORDER BY can't use one. Instead, the website only accepts sorts from a fixed list in the SQL file: {{ sorts|join(", ")|safe }}. Anything else is ignored.

/songs?sort=name {{ ui.icon("arrow") }} sorted by name /songs?sort=…;DROP TABLE song {{ ui.icon("arrow") }} ignored
3

Passwords are never saved

The database keeps only a hash: a scrambled version that can't be turned back. At login, the website hashes what you type and compares. Here is what the listener table has for {{ demo.username }} (password music330):

{{ demo.password_hash }}

Hashing the same password twice gives two different hashes, because each one gets a random salt (the text between the two $ signs). So two listeners with the same password don't have the same hash:

{% for h in fresh_hashes %}
{{ h }}
{% endfor %}

scrypt is also slow on purpose, so guessing millions of passwords takes too long.

4

Form tokens (CSRF)

Another website could hide a form that posts to music_db, using your login. So every form here has a secret token that only our pages know. Your token starts with {{ token_start }}…. A form without the right token gets “400 Bad Request”.

5

A MySQL user with few rights

The website doesn't log in to MySQL as root. Its user can read and change rows, but it can't drop or change tables. Even a bug can't delete a table. SHOW GRANTS says:

{% endfor %}

And the playlists are private: their SQL always checks the owner, WHERE playlist_id = … AND listener_id = <me>.
